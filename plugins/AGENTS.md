# AGENTS.md — `plugins/`

You are in the plugin tree. Almost every MMGIS feature lives here. This file is the contract summary;
[README.md](./README.md) in this directory is the full reference.

## The rule that matters most

**Add functionality as a plugin. Do not add branching to core to accommodate it.** Rendering and
feature-click dispatch are fully plugin-driven — core no longer switches on layer type or `kind` to
decide *how to draw* or *what a click does*. (Legacy `type === 'vector'` checks do survive in
`src/essence/Basics/Layers_/` for cross-cutting concerns like pairings, attachments, and filtering;
they are debt, not a pattern to copy.) If your change requires editing core to teach it about your
feature, you are almost certainly using the wrong extension point — re-read this file and
[README.md](./README.md) first.

## Layout

```
plugins/
├── plugin-cli.js            # the CLI (npm run plugins -- <cmd>)
├── plugin-registries.json   # known plugin sources
├── plugin-state.json        # enable/disable state — gitignored, instance-specific
├── core/                    # committed, version-controlled
│   ├── tools/               # 11 toolbar tools
│   ├── backend/             # 13 Express feature modules
│   ├── components/          # 2 always-on UI components
│   ├── interactions/        # 14 feature click/hover pipeline steps
│   └── layertypes/          # 12 layer types
└── <org--repo>/             # installed from git — gitignored
```

`plugins/<container>/<type>/<PluginName>/`. Directory names are plural; the manifest `type` is
**singular**. `core` is discovered first, then other containers alphabetically; a plugin with
`"overridable": false` cannot be overridden, and one marked `required` cannot be disabled.

## Always

```bash
npm run plugins -- create <tool|backend|component|interaction|layertype> <Name> --container my-plugins
npm run plugins -- validate            # manifest + renderer-module contract checks
npm run plugins -- activate            # regenerate tools/components/interactions registries
npm run plugins -- list --json         # every command supports --json
npm run plugins -- info <plugin-id>
```

- **Scaffold with `create` rather than hand-writing a plugin.** It emits a correct `plugin.json`, the
  entry module(s), a `metaconfig.json` where the type needs one, and a `tests/<name>.spec.js`.
  Scaffolding into `core` requires `--force`.
- **Run `validate` before you commit.** It runs at server startup too, so an invalid manifest is a
  broken app, not a warning.
- **Never hand-edit `src/pre/tools.js`, `src/pre/components.js`, `src/pre/interactions.js`,
  `src/pre/layertypes.js`, `src/pre/layerattachments.js`.** Generated by `API/updateTools.js`,
  gitignored. **`activate` only regenerates tools, components, and interactions** — the layer-type
  and layer-attachment registries are rebuilt by a server start or `npm run build`, or explicitly via
  `node -e "require('./API/updateTools').updateLayerTypes()"`. A new layer type that doesn't appear
  after `activate` is this, not your manifest.
- Plugin tests are colocated in the plugin's own `tests/` directory and run with
  `npm run test:plugins` (Playwright).
- Frontend plugin code imports core through webpack aliases (e.g. `@basics/Layers_/Layers_`), not
  long relative paths.

## The five types

| `type` | Required manifest fields | Entry contract |
|---|---|---|
| `tool` | `name`, `paths` | Object with `make()` (open) and `destroy()` (close); optional `getUrlString()`. `separatedTool`, `toolbarPriority`, `config` control placement and the Configure-page UI. |
| `backend` | `name` (keyed by directory) | `plugin.js` exports `{ onceInit, onceStarted, onceSynced }`; mounts routers from `routes/`, Sequelize models in `models/`. Declare `routes.prefix`/`routes.auth`. |
| `component` | `name`, `paths` | Same shape as a tool, but always-on rather than toolbar-activated. |
| `interaction` | `name`, `interactionId`, `paths` | Object with `use(ctx)` (may be async). Declare `phase` (`preamble`/`main`/`postamble`), `order`, and optionally `suppresses`, `kindAlias`, `applicableLayerTypes`, `applicableEvents`. |
| `layertype` | `name`, `typeId`, `paths` (unless non-rendering, e.g. `header`) | Renderer module per surface exporting `make` (required) plus any of `load`, `destroy`, `setOpacity`, `setVisibility`, `setStyle`, `timeChange`. Also declare `capabilities.renderers` and `supportedData`. |

`layerattachment` exists in the CLI and validator but **is not implemented yet — do not use it.**

## Layer types — the 20% you need before reading the full doc

- A renderer module is `export default { …operations }`, one module per surface/engine, wired up by
  `paths` (`map`, `globe.cesium`, `globe.lithosphere`) and declared in `capabilities.renderers`.
  **A declared engine with no module — or a module for an undeclared engine — is a startup error.**
- **Only `make` is required.** Core supplies a default for every other operation (generic removal for
  `destroy`, a uniform applier for `setOpacity`/`setVisibility`, no-op for `setStyle`, reload for
  `timeChange`), so implement an operation only where the engine has no uniform primitive. This is why
  Leaflet modules rarely define `setOpacity` while Cesium modules usually must.
- Each operation may be a bare function (shorthand for `{ main }`) or `{ before, main, after }`;
  supplying `main` *is* the override. `make` additionally supports `afterCommit`, which runs after the
  make-lock releases.
- Reach the engine through the neutral `MapRenderer` / `GlobeRenderer` primitives; drop to `mctx.raw`
  / `gctx.renderer` only for genuinely engine-specific work.
- Dispatcher and JSDoc typedefs: `src/essence/Basics/Layers_/interface/LayerInterface.js`.

Full contract, signatures, and checklist: **[core/layertypes/README.md](./core/layertypes/README.md)**.

## Interactions — what replaced `Kinds`

A layer's feature-click behavior is a **pipeline**, not a single hardcoded "kind":
`preamble → main → postamble`, ordered by `order` within each phase. Core always applies the
preamble/postamble; the `main` phase comes from the layer's explicit `layerData.interactions.<event>`,
or from its legacy `kind` string mapped through each interaction's `kindAlias`, or from the layer
type's `capabilities.defaultInteractions`. An interaction can `suppress` a default it replaces (e.g.
`info:open` suppresses `info:silent`). `use(ctx)` receives `Map_`, `feature`, `layer`, `layerName`,
`layerData`, `layerVar`, `event`, `eventType`, `additional`, plus `stop` to halt the pipeline and
`state` to pass data downstream. The runner
(`src/essence/Basics/InteractionRunner/InteractionRunner.js`) hardcodes no interaction IDs —
all orchestration is in the manifests.

## Where things are wired

| File | Role |
|---|---|
| `API/pluginDiscovery.js` | `discoverPlugins()` — scans all containers |
| `API/pluginValidation.js` | `validatePluginConfig()` — manifest schema per type |
| `API/updateTools.js` | build-time discovery → generates the `src/pre/*` registries |
| `API/setups.js` | runtime backend discovery → loads `plugin.js` hooks |
| `scripts/resolve-plugin-deps.js` | aggregates plugin npm/pip/conda dependencies |
