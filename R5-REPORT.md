## 3. The seams between the families

- **type → attachment**: `capabilities.defaultAttachments: {"hazard_buffer":
  {"severityProp":"severity","classProp":"hazard_class","severityScale":1}}` in the layertype
  manifest; the attachment reads them from `ctx.config` and defaults them in `propsOf()`. The
  docs told me to do exactly this (plugins/README.md:373-385, layertypes/README.md:475-503) and
  core implements it (`src/essence/Basics/Layers_/registry/attachmentDefaults.js`).
- **type → interaction**: `capabilities.defaultInteractions.click: ["hazard:report"]` —
  documented, layertypes/README.md:457-471.
- **attachment → interaction**: **I invented this shape.** The attachment stashes its computed
  buffers as `_buffers` on the object it returns, and the interaction walks
  `L_.layers.attachments` looking for a `hazard_buffer` key. The docs sanction the *mechanism*
  ("read what it left behind", plugins/README.md:371, 387) but nothing defines a payload
  contract, so `_buffers` is a private convention between two plugins that a rename breaks
  silently.
- **The gap that hurts**: the type's `defaultAttachments` is static JSON. My layertype also
  offers `variables.hazard.severityProp` in Configure, but an admin-typed value there reaches
  only `normalize`/`legend` — it cannot reach the attachment, because the manifest literal is
  fixed at build time. So the "declare it once" promise only holds for hardcoded facts, not
  admin-editable ones.

## 4. Where I wanted to call another plugin and couldn't

Two places.

(a) The interaction wanted "give me the hazard_buffer attachments" — there is no lookup by
`attachmentId` (explicitly refused, plugins/README.md:387), so I scan every layer's attachments
and duck-type.

(b) The interaction's natural host is the *candidate landing point* layer, not a `hazardzone`
layer, and a layer type can only declare defaults for **its own** layers. There is no
declarative way for my feature to say "put `hazard:report` on the site-selection layer too" — an
admin must add it by hand in that layer's Interactions tab. That is the single biggest
multi-family gap I hit.

## 5. Failed silently

Nothing I could catch without a browser, and that's the point — validate was green from the
first minute with three stub plugins.

One likely silent failure I reasoned about but did not confirm: `resolveAttachmentConfig` is
`{...declared, ...own}`, so if Configure writes `''` for the empty "Severity Property" field, the
empty string wins over the type's declared value, contradicting plugins/README.md:385 ("empty
means as the type declared").

## 6. Docs friction

- plugins/README.md:371 says the attachment lives at
  `L_.layers.attachments[layerName][attachmentId]`; layerattachments/README.md:73 says the key is
  `capabilities.host.sublayerKey` (defaulting to attachmentId), and core keys the outer map by
  the layer's uuid-name. Three near-miss statements of the same fact.
- The task said `npm run test:unit`; plugin tests are **not** in it — they need
  `npm run test:plugins:unit`. Only a comment in the scaffolded spec says so.
- `eslint` on a plugin dies without `NODE_ENV` set (babel-preset-react-app). Nothing documents
  it; `NODE_ENV=test npx eslint …` works.
- The layerattachment scaffold defaults `config.tab` to `Attachment - Markers` even for a polygon
  attachment, and its scaffolded test hardcodes the scaffolded `configPath` — change the path and
  the test fails for a reason unrelated to your code.

## 7. What I liked

`create layertype --extends vector` gave a genuinely one-file type; the scaffolds are honest
files with the "don't override a working default" comment table; `plugins/README.md`'s "You're
not done when validate passes" and "One feature, several plugins" sections predicted almost
exactly the container I ended up with; validate's cross-family checks (attachment refusing a type
that declares it) are real checks, not lint.

## 8. Top 3 recommendations

1. Make cross-family facts *runtime-resolved*, not manifest-literal: let a layer type expose a
   `provides` block (or a resolver on its `config` surface) whose values core feeds into
   `defaultAttachments`/interaction config, so an admin-edited property name propagates instead of
   only a hardcoded one.
2. Give a documented read path between families: a core helper
   (`L_.attachmentsOfType('hazard_buffer')`) plus a declared "payload" key in the attachment
   manifest, so an interaction isn't duck-typing a `_`-prefixed field across every layer.
3. Make the container a first-class unit: `plugins -- create feature <Name>` scaffolding the trio
   + `lib/` wired together, a container-level manifest for shared settings, and a `validate`
   cross-check that a container's declared seams (attachmentIds, interactionIds,
   `applicableLayerTypes`) actually line up — plus a way to target interactions at layers of
   *other* types.
